🌱 Beginner — Git Fundamentals

⚙️ 1. Installation & Identity Setup Beginner ▼

Before anything else, install Git and tell it who you are. Every commit records your name and email, so this matters for team work and open-source contributions.

Install (Ubuntu / Debian)
sudo apt update && sudo apt install git -y
Install (macOS via Homebrew)
brew install git
Set your identity (run once globally)
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
git config --global core.editor "code --wait"   # VS Code as default editor
git config --global init.defaultBranch main      # modern default branch name
Verify
git config --list
Production tip: Use a work email in repos that belong to your employer. You can override the global config per-repo: git config user.email "work@company.com" inside that repo folder.
📂 2. Creating & Cloning Repositories Beginner ▼

A Git repository is a folder tracked by Git. You either start one from scratch (init) or copy an existing one (clone).

Start a new repo
mkdir my-project && cd my-project
git init
Clone a remote repo
git clone https://github.com/owner/repo.git
git clone https://github.com/owner/repo.git my-folder   # custom folder name
Production tip: Prefer SSH cloning in CI/CD pipelines: git clone git@github.com:owner/repo.git
📝 3. Staging & Committing Changes Beginner ▼

Git has three areas: working directory (your files), staging area / index (what will go into the next commit), and the commit history. You selectively stage changes before committing.

Check what changed
git status            # overview
git diff              # unstaged changes
git diff --staged     # staged changes (ready to commit)
Stage files
git add file.txt          # stage one file
git add src/              # stage a directory
git add .                 # stage everything in the current folder
git add -p                # interactive: stage specific hunks (powerful!)
Commit
git commit -m "feat: add login form"
git commit -am "fix: correct typo"   # stage all tracked changes + commit
Production tip: Follow Conventional Commits: type(scope): description — e.g., feat(auth): add OAuth2 login, fix(api): handle null response. This enables automated changelogs and semantic versioning.
📜 4. Viewing Commit History Beginner ▼

git log shows the commit history. Learn its flags — they are invaluable for code reviews and debugging regressions.

Common log commands
git log                             # full history
git log --oneline                   # compact view
git log --oneline --graph --all     # visual branch graph
git log -10                         # last 10 commits
git log --author="Alice"            # filter by author
git log --since="2 weeks ago"       # filter by date
git log --grep="fix"                # filter by commit message
git log -p file.txt                 # history of changes to a specific file
git show abc1234                    # show a specific commit
Alias tip: Add this to your ~/.gitconfig for a beautiful graph: git config --global alias.lg "log --oneline --graph --all --decorate" Then run git lg.
☁️ 5. Working with Remotes (push, pull, fetch) Beginner ▼

Remotes are versions of your repo hosted elsewhere (GitHub, GitLab, etc.). push uploads your commits; fetch downloads without merging; pull is fetch + merge.

Remote commands
git remote -v                          # list remotes
git remote add origin <url>            # add a remote
git push origin main                   # push branch to remote
git push -u origin main                # push & set upstream tracking
git fetch origin                       # download changes (don't merge yet)
git pull origin main                   # fetch + merge
git pull --rebase origin main          # fetch + rebase (cleaner history)
Production tip: Prefer git pull --rebase over plain git pull to avoid unnecessary merge commits in shared branches. Set it as the default: git config --global pull.rebase true
🌿 6. Branching & Merging Beginner ▼

Branches let you work on features or bug fixes in isolation without affecting the main codebase. Merging brings those changes back.

Branch operations
git branch                        # list local branches
git branch -a                     # list all branches (including remote)
git branch feature/login          # create a branch
git checkout feature/login        # switch to a branch
git checkout -b feature/login     # create AND switch (one command)
git switch -c feature/login       # modern alternative (Git 2.23+)
git branch -d feature/login       # delete merged branch
git branch -D feature/login       # force-delete unmerged branch
Merge
git checkout main
git merge feature/login           # merge feature into main
git merge --no-ff feature/login   # always create a merge commit (keeps history)
Production tip: Use short-lived feature branches. Long-lived branches drift far from main and cause painful merge conflicts. Merge or rebase at least daily.
↩️ 7. Undoing Changes Beginner ▼

Git gives you multiple ways to undo — the right one depends on how far back you want to go and whether the commits are already pushed.

Discard working-directory changes
git restore file.txt              # discard unstaged changes in a file
git restore .                     # discard ALL unstaged changes
git clean -fd                     # remove untracked files & directories
Unstage
git restore --staged file.txt     # unstage a file (keep working-dir change)
Amend the last commit (not yet pushed)
git commit --amend -m "corrected message"  # rewrite last commit message
git commit --amend --no-edit               # add staged files to last commit
Revert a pushed commit (safe — creates a new commit)
git revert abc1234        # creates a new "undo" commit
git revert HEAD           # revert the latest commit
Reset (use with caution on shared branches)
git reset --soft HEAD~1   # undo last commit, keep changes staged
git reset --mixed HEAD~1  # undo last commit, keep changes unstaged (default)
git reset --hard HEAD~1   # undo last commit AND discard all changes
Production rule: Never use git reset --hard or git push --force on shared branches like main or develop. Use git revert instead.
🚫 8. Ignoring Files with .gitignore Beginner ▼

.gitignore prevents build artifacts, secrets, and dependencies from being tracked. It should be committed to the repo.

Example .gitignore (Node.js project)
node_modules/
dist/
.env
.env.local
*.log
.DS_Store
coverage/
Stop tracking a file already committed
git rm --cached .env       # remove from index, keep local file
echo ".env" >> .gitignore
git commit -m "chore: untrack .env"
Production tip: Use gitignore.io to generate a .gitignore for your stack in seconds. Never commit .env files containing secrets.

⚡ Advanced — Power-User Git

🔀 9. Rebase — Rewrite History Advanced ▼

git rebase replays your commits on top of another branch, producing a linear history without merge commits. Interactive rebase (-i) lets you squash, reorder, edit, or drop commits before sharing.

Standard rebase
# Update feature branch with latest main changes
git checkout feature/login
git fetch origin
git rebase origin/main
Interactive rebase (last 3 commits)
git rebase -i HEAD~3
# In the editor, commands per line:
#   pick   - keep as-is
#   reword - keep but edit message
#   squash - meld into previous commit
#   fixup  - like squash but discard message
#   drop   - remove this commit entirely
After resolving conflicts during rebase
git status                # see conflicting files
# edit the conflicting files, then:
git add <resolved-file>
git rebase --continue
# or abort entirely:
git rebase --abort
Production tip: Squash WIP commits into one meaningful commit before opening a pull request. Reviewers thank you. Never rebase commits already on a shared remote branch.
🍒 10. Cherry-pick — Apply Specific Commits Advanced ▼

git cherry-pick applies one or more commits from any branch onto the current branch. Useful for backporting a bug fix to a release branch without merging everything.

Cherry-pick a commit
git cherry-pick abc1234            # apply one commit
git cherry-pick abc1234 def5678    # apply multiple commits in order
git cherry-pick abc1234..def5678   # apply a range of commits
Cherry-pick without auto-committing
git cherry-pick -n abc1234         # stage changes but don't commit yet
git status                         # review, then commit manually
Production use-case: A critical security fix was merged to main. You need it in the release/v2.3 branch immediately without pulling all of main. Cherry-pick that fix commit onto the release branch.
🧳 11. Stash — Temporarily Shelve Changes Advanced ▼

git stash saves your uncommitted work to a stack so you can switch context (e.g., fix an urgent bug on another branch) then come back to resume.

Stash commands
git stash                        # stash tracked changes
git stash -u                     # stash including untracked files
git stash push -m "WIP: user auth" # stash with a descriptive name
git stash list                   # view all stashes
git stash pop                    # re-apply most recent stash & remove it
git stash apply stash@{2}        # apply a specific stash (keep it in list)
git stash drop stash@{0}         # delete a specific stash
git stash clear                  # delete all stashes
Pro tip: Use descriptive stash names (git stash push -m "description"). A stash list full of unnamed entries is hard to manage after a few days.
🏷️ 12. Tags & Releases Advanced ▼

Tags mark specific commits as release points (e.g., v1.4.0). Annotated tags store extra metadata and are the standard for releases.

Tag commands
git tag                            # list tags
git tag v1.0.0                     # lightweight tag
git tag -a v1.0.0 -m "Release 1.0.0"  # annotated tag (preferred)
git tag -a v1.0.0 abc1234 -m "..."    # tag a past commit
git push origin v1.0.0             # push one tag
git push origin --tags             # push all tags
git tag -d v1.0.0                  # delete local tag
git push origin --delete v1.0.0   # delete remote tag
Production tip: Follow Semantic Versioning: MAJOR.MINOR.PATCH. Pair tags with GitHub Releases and a generated changelog for professional release management.
⚔️ 13. Resolving Merge Conflicts Advanced ▼

Conflicts happen when two branches change the same lines. Git marks the conflicting sections; you decide which version (or a blend) to keep.

Conflict markers in a file
<<<<<<< HEAD (your current branch)
const port = 3000;
=======
const port = 8080;
>>>>>>> feature/port-change (incoming branch)
Resolve workflow
# 1. Open conflicting files and edit them to the desired result
# 2. Remove all conflict markers (<<<, ===, >>>)
# 3. Stage the resolved files
git add file.txt
# 4. Complete the merge / rebase
git merge --continue
# or
git rebase --continue
Use a merge tool
git config --global merge.tool vscode
git mergetool   # opens all conflicting files in the configured tool
Production tip: Use git diff --diff-filter=U to quickly list only conflicting files. VS Code's built-in merge editor (three-pane view) makes conflict resolution much faster.
🔍 14. Debugging — blame & bisect Advanced ▼

git blame shows who last changed each line of a file. git bisect performs a binary search through history to find the commit that introduced a bug.

git blame
git blame src/api.js              # who changed each line
git blame -L 10,25 src/api.js    # only lines 10–25
git blame -w src/api.js          # ignore whitespace changes
git bisect
git bisect start
git bisect bad                   # current commit is broken
git bisect good v2.0.0           # this tag was working

# Git checks out a midpoint commit — test your app, then:
git bisect good   # if this commit is fine
git bisect bad    # if this commit is broken

# Git narrows down; repeat until it prints the culprit commit
git bisect reset  # return to original HEAD when done
Production tip: Bisect runs in O(log n) steps — it finds the offending commit among 1000 commits in ~10 steps. Automate it: git bisect run npm test (exits 0 = good, non-0 = bad).
🧵 15. Reflog — Git's Safety Net Advanced ▼

git reflog records every movement of HEAD — even commits that were reset or branches that were deleted. It is your last resort to recover "lost" work.

Recover a lost commit
git reflog                        # list all HEAD movements with short SHAs
# Find the SHA of the lost commit, then:
git checkout abc1234              # inspect it
git branch recover-branch abc1234 # recreate a branch at that commit
Recover after a bad reset --hard
git reflog
# e.g., HEAD@{2} is the commit before the bad reset
git reset --hard HEAD@{2}
Good to know: Reflog entries expire after 90 days by default. It only exists locally — it is not pushed to remotes.

🚀 Pro — Production Workflows

🪝 16. Git Hooks — Automate Quality Gates Pro ▼

Git hooks are scripts that run automatically before or after Git events (commit, push, merge). Use them to enforce quality standards without relying on developer memory.

pre-commit hook — run linter before every commit
#!/bin/sh
# .git/hooks/pre-commit  (make executable: chmod +x .git/hooks/pre-commit)
npm run lint || exit 1   # block the commit if lint fails
commit-msg hook — enforce Conventional Commits
#!/bin/sh
# .git/hooks/commit-msg
msg=$(cat "$1")
pattern="^(feat|fix|docs|style|refactor|test|chore)(\(.+\))?: .+"
if ! echo "$msg" | grep -qE "$pattern"; then
  echo "ERROR: Commit message must follow Conventional Commits format."
  echo "Example: feat(auth): add OAuth login"
  exit 1
fi
Share hooks via Husky (Node.js projects)
npm install --save-dev husky
npx husky init
# Edit .husky/pre-commit to add your commands
Production tip: Hooks in .git/hooks/ are local and not committed. Use Husky or pre-commit to share hooks across the team via the repo itself.
🗺️ 17. Git Workflows — Gitflow vs Trunk-Based Pro ▼

How a team branches and merges is just as important as individual Git skills. Two dominant strategies:

Gitflow — structured release cycle
# Branches: main, develop, feature/*, release/*, hotfix/*
# Install gitflow extension (optional helper)
git flow init

# Start a feature
git flow feature start user-auth

# Finish it (merges to develop)
git flow feature finish user-auth

# Start a release
git flow release start 1.2.0
# ... test, bump version ...
git flow release finish 1.2.0   # merges to main & develop, creates tag
Trunk-Based Development — high velocity CI/CD
# Everyone commits to "main" (the trunk) at least daily
# Short-lived feature branches (< 2 days) merged via PR

git checkout -b feat/short-task
# ... make change ...
git commit -m "feat: small focused change"
git push origin feat/short-task
# Open PR → CI passes → squash merge → delete branch
Choose based on release cadence: Use Gitflow for versioned products with scheduled releases (mobile apps, packaged software). Use Trunk-Based for web services with continuous deployment — it pairs perfectly with feature flags.
🧩 18. Submodules — Nesting Repositories Pro ▼

Submodules allow you to embed one Git repository inside another while keeping their histories independent. Used for shared libraries or vendored dependencies.

Submodule commands
git submodule add https://github.com/owner/lib.git libs/mylib
git submodule update --init --recursive   # init & clone all submodules
git submodule update --remote             # pull latest commits in submodules
git submodule foreach git pull origin main  # update all submodules
Cloning a repo with submodules
git clone --recurse-submodules https://github.com/owner/repo.git
Production tip: Submodules have a steep learning curve. Consider Yarn/npm Workspaces or a monorepo tool (Nx, Turborepo) for JavaScript projects. Submodules shine for firmware/embedded projects with language-agnostic shared code.
⚠️ 19. Force Push — When and How to Do It Safely Pro ▼

Sometimes you need to rewrite the history of a remote branch (e.g., after an interactive rebase or amending a pushed commit). Plain --force is dangerous. Use --force-with-lease instead.

Safe force push
# WRONG — overwrites any remote changes you haven't fetched:
git push --force origin feature/login

# CORRECT — fails if someone else pushed since your last fetch:
git push --force-with-lease origin feature/login
Protect production branches (GitHub)
# In GitHub: Settings → Branches → Add branch protection rule
# Enable:
#  ✔ Require pull request reviews before merging
#  ✔ Require status checks to pass
#  ✔ Do not allow bypassing the above settings
#  ✔ Block force pushes
Rule of thumb: Force push is acceptable only on your own feature branches. It is never acceptable on main, develop, or any shared branch.
⚡ 20. Performance — Shallow Clones & Sparse Checkout Pro ▼

Large monorepos and long-lived projects can have slow clones. These techniques dramatically speed up CI pipelines and local onboarding.

Shallow clone — fetch only recent history
git clone --depth 1 https://github.com/owner/repo.git      # only latest commit
git clone --depth 50 https://github.com/owner/repo.git     # last 50 commits
# Unshallow later if needed:
git fetch --unshallow
Sparse checkout — only download specific directories
git clone --filter=blob:none --sparse https://github.com/owner/monorepo.git
cd monorepo
git sparse-checkout set packages/my-app packages/shared-lib
CI/CD tip: In GitHub Actions, always use actions/checkout@v4 with fetch-depth: 1 (the default) for faster pipelines. Only set fetch-depth: 0 when you need the full history (e.g., for semantic-release or changelog generation).
